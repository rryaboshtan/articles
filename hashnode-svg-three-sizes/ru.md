# SVG viewBox vs width/height vs CSS: три размера, из‑за которых «ломаются» иконки

Выгружаешь из Figma иконку 24×24 — а в браузере она то крошечная, то огромная, то чёткая, но уже внутри размытого PNG. Файл почти никогда не «сломан». В нём сразу **три разных размера**, и твои инструменты просто послушали не тот.

Обычный совет — «не трогай `viewBox`». Он верный, но сам по себе не спасает. Если у вас дизайн‑система, иконки в React или PNG для писем, нужно понимать: что из трёх — **жёсткий контракт**, а что — просто значение по умолчанию.

![Три сигнала размера SVG: viewBox — контракт, width/height — значение по умолчанию, CSS и props — размер на экране](./images/01-three-sizes.svg)

## SVG viewBox vs width/height vs CSS — три размера

Типичный экспорт из Figma выглядит безобидно:

```xml
<svg
  xmlns="http://www.w3.org/2000/svg"
  width="24"
  height="24"
  viewBox="0 0 24 24"
>
  <path d="…" />
</svg>
```

Тут сразу **три независимых сигнала**:

| Сигнал | Зачем нужен | Кто на него смотрит |
| --- | --- | --- |
| **`viewBox`** | Система координат: «рисунок живёт в квадрате 24×24» | Движок отрисовки, `preserveAspectRatio`, нормальный пайплайн иконок |
| **Атрибуты `width` / `height`** | Размер «из коробки», пока больше никто не задал | Браузер (если CSS молчит), часть PNG‑экспортёров, копипаст «как есть» |
| **CSS и props** (`className`, `width={32}`) | Какой размер нужен **здесь**, в интерфейсе | React, вёрстка, дизайн‑токены |

Когда они расходятся, получаются знакомые сюрпризы:

- В `<img src="icon.svg">` всё нормально, в JSX — уже нет
- `<Icon width={16} />` будто ничего не меняет (побеждает CSS или порядок атрибутов)
- Retina‑PNG мыльный: в PNG ушёл размер из атрибутов, а на экране показывают другой
- В `viewBox` написано `0 0 24 24`, а path рисовали в диапазоне `0…100` — пустые поля или обрезанная иконка

**Коротко:** `viewBox` — контракт. Атрибуты — запасной вариант. CSS и props — реальный размер на экране.

### Как браузер выбирает размер

У inline SVG и у `<img src="*.svg">` логика **разная**.

**Inline SVG** в HTML или JSX — обычное DOM‑дерево. Сначала смотрят CSS, потом атрибуты на корневом `<svg>`.

**`<img>` и `background-image`** видят файл как картинку. Браузер ищет «свой» размер внутри: абсолютные `width`/`height` у корня, иначе пропорции из `viewBox`, иначе классический запасной вариант — **300×150**.

На практике для иконок порядок такой:

1. CSS, flex или grid задают **коробку на экране**.
2. Если CSS молчит — берут атрибуты `width`/`height` (голое `24` в HTML = `24px`).
3. Если и их нет — остаётся `viewBox` и пропорции. А если конкретного размера нет вообще, часто рисуется **300×150**. Так после «чистки атрибутов» маленькая иконка внезапно становится баннером.
4. `viewBox` по‑прежнему говорит, **что** рисовать внутри коробки. CSS и атрибуты решают только, **насколько крупно** эта коробка.

Единицы в `viewBox` — это не CSS‑пиксели, а внутренняя система координат. `stroke-width="1.5"` значит «полторы таких единицы». Увеличишь иконку с 24 до 48 CSS‑пикселей — линия на экране станет вдвое толще, если не включён `vector-effect="non-scaling-stroke"`.

Вся статья, по сути, про эту проекцию.

## Как устроен размер SVG: координаты, проекция, пиксели

Удобно думать про SVG как про canvas, только в XML:

1. **Координаты** — числа в `d`, `cx`, `x` живут в единицах `viewBox`.
2. **Проекция** — движок натягивает этот прямоугольник на коробку в вёрстке или на сетку пикселей при экспорте.
3. **Пиксели** — появляются только когда нужен растр: PNG, `<canvas>`, скриншот, «сплющивание» в PDF.

![Система координат проецируется на экранную коробку и превращается в пиксели только при растре](./images/02-mapping-model.svg)

Если проекция кривая, крутить `stroke-width` бесполезно. Сначала почини `viewBox` и то, куда он ложится.

### Пример: иконка с полями внутри фрейма 24×24

В дизайн‑инструментах часто так: фрейм 24, сама иконка примерно 16, по центру.

```xml
<svg width="24" height="24" viewBox="0 0 24 24">
  <!-- рисунок примерно в диапазоне 4…20 по обеим осям -->
  <path d="M8 6h8v12H8z" />
</svg>
```

| Что делаешь | Что получается |
| --- | --- |
| Вставляешь inline в кнопку 24px | Выглядит нормально |
| Делаешь PNG 24×24 и показываешь его как 16 CSS‑пикселей | Края мыльные |
| Убираешь `width`/`height`, оставляешь `viewBox`, размер задаёшь через CSS или props | Чётко при любом размере |

Для системы иконок нужна третья строка: **стабильный `viewBox`, без зашитого размера в файле, размер задаётся там, где иконку используют.**

### `preserveAspectRatio` — тихий четвёртый рычаг

Если пропорции CSS‑коробки не совпадают с `viewBox`, решает `preserveAspectRatio`:

| Значение | Поведение |
| --- | --- |
| `xMidYMid meet` (по умолчанию) | Вписать внутрь, пропорции сохранить, могут появиться поля |
| `xMidYMid slice` | Заполнить коробку, пропорции сохранить, края могут обрезаться |
| `none` | Растянуть как получится (для иконок почти всегда плохо) |

Если после `width: 32px; height: 20px` иконка «сплющилась», path ни при чём — ты изменил коробку и не сохранил (или сохранил) пропорции.

## Почему viewBox «не работает»: координаты врут

```xml
<!-- path в пространстве 0…100, а viewBox врёт -->
<svg width="24" height="24" viewBox="0 0 24 24">
  <circle cx="50" cy="50" r="40" />
</svg>
```

Центр круга лежит за пределами объявленного квадрата. Можно сколько угодно крутить размер в CSS — диск всё равно обрежется. Сломан не стиль кнопки, а контракт `viewBox`.

![Неверный viewBox обрезает рисунок, который нарисован в другом диапазоне координат](./images/05-viewbox-lie.svg)

**Как проверить за полминуты**

Это три разных прямоугольника — их нельзя путать:

| Что смотришь | В каких единицах | На что отвечает |
| --- | --- | --- |
| `viewBox` | единицы рисунка | какой контракт ты **заявил** |
| `el.getBBox()` | единицы рисунка | где реально лежат «чернила» (без CSS‑размера) |
| `el.getBoundingClientRect()` | CSS‑пиксели | какую коробку заняла вёрстка на экране |

```js
const svg = document.querySelector('svg');
const ink = svg.querySelector('g, path, circle');
console.log(svg.getAttribute('viewBox'));     // заявленный контракт
console.log(ink.getBBox());                   // реальные границы рисунка
console.log(svg.getBoundingClientRect());     // коробка на экране
```

Если `getBBox()` примерно `0…100`, а в `viewBox` стоит `0 0 24 24`, файл врёт. CSS это не починит.

**Как это часто приходит из Figma:** экспорт оборачивает рисунок в `<g transform="translate(4 4)">` (а то и в несколько translate подряд), а у корня по‑прежнему `viewBox="0 0 24 24"`. В макете всё выглядело по центру, в файле контракт уже не совпадает с координатами path. Это чинят один раз — пересчитывают `viewBox` по `getBBox()` или разворачивают transform при экспорте, — а не правят `translate` в каждом pull request.

Не ставь `0 0 24 24` только потому, что «у нас иконки 24». Сначала посмотри реальные границы, потом выберите сетку команды (20 или 24) и приведите файлы к ней.

## Почему в React «ломается» размер иконки

Браузер часто прощает кривой HTML. React делает конфликт явным — через **порядок props**:

```jsx
// В компоненте по умолчанию 24. В месте вызова просят 16. Кто победит?
export function Icon(props) {
  return (
    <svg
      viewBox="0 0 24 24"
      width={24}
      height={24}
      fill="none"
      {...props}
    >
      <path d="…" stroke="currentColor" strokeWidth={1.5} />
    </svg>
  );
}

<Icon width={16} height={16} className="text-slate-700" />
```

Если `{...props}` стоит в конце — побеждает `16`. Перенесёшь spread выше — место вызова тихо проиграет. Команда может неделю спорить про «сломанные иконки», пока кто‑то не посмотрит порядок атрибутов.

![Порядок props в React: если spread стоит рано, размер с места вызова проигрывает; если в конце — побеждает](./images/03-react-prop-order.svg)

**Как это выглядит в реальном PR:**

```jsx
// БЫЛО — в Storybook на 24 всё ок, в плотном тулбаре «сломано»
export function Chevron(props) {
  return (
    <svg viewBox="0 0 24 24" {...props} width={24} height={24}>
      <path d="…" stroke="currentColor" strokeWidth={1.5} />
    </svg>
  );
}
// <Chevron width={16} /> всё ещё рисуется как 24 — spread проиграл

// СТАЛО — один способ задать размер, место вызова побеждает, viewBox не трогаем
export function Chevron({ size = 24, ...props }) {
  return (
    <svg viewBox="0 0 24 24" width={size} height={size} aria-hidden="true" {...props}>
      <path d="…" stroke="currentColor" strokeWidth={1.5} />
    </svg>
  );
}
```

Отдельно — **типы в React Native**. В вебе иногда прокатывает `width="24"` строкой; в `react-native-svg` нужен `width={24}` числом. Конвертер с кавычками «ломает размер» только на мобиле — и снова летит тикет «SVG сломан».

### Удобный базовый вариант для иконок интерфейса

```jsx
export function Icon({ size = 24, ...props }) {
  return (
    <svg
      viewBox="0 0 24 24"
      width={size}
      height={size}
      fill="none"
      aria-hidden="true"
      {...props}
    >
      <path d="…" stroke="currentColor" strokeWidth={1.5} />
    </svg>
  );
}
```

`viewBox` не трогай. Размер задавай одним способом. Не зашивай второй размер в CSS, а третий — ещё и в пайплайне PNG.

**Ловушка CSS:** если в стилях написано `.icon { width: 24px !important; }`, props будут казаться «сломанными» даже при идеальном JSX. У размера на экране должен быть один хозяин.

В React Native та же схема: числовые props (`width={24}` на `<Svg>`). Контракт тот же: `viewBox` в файле, размер — в месте вызова. Если нужно быстро получить JSX, удобно вставить разметку в [конвертер SVG → React](https://getsvgeditor.com/svg-to-react) — там же рядом вкладка React Native, чтобы сверить числовые props с превью.

### Если компоненты собираете через SVGR

Когда из `.svg` генерируете компоненты:

- `viewBox` оставляйте.
- Жёсткие `width`/`height` лучше заменить на prop `size` (или на переопределяемые `width`/`height`).
- `{...props}` должен уметь перебить размер и атрибуты доступности.
- Цвет интерфейсных иконок — через `currentColor`, не через зашитый `#000`.

## Почему PNG из SVG на retina выглядит мыльно

PNG всё равно, какие у вас токены в дизайн‑системе. Ему важно одно: **сколько пикселей вы попросили при экспорте**.

Типичный провал при передаче макета:

1. В SVG в атрибутах стоит 24×24  
2. Экспортируешь PNG 24×24  
3. Показываешь его на 48 CSS‑пикселях на экране 2× **без** отдельного 2×‑файла  
4. В тикете пишут: «SVG плохо выглядит»

С SVG всё было в порядке. Не хватило пикселей в PNG.

![Нужный размер PNG = размер в CSS × плотность экрана](./images/04-retina-pixel-budget.svg)

### Сколько пикселей экспортировать

| Размер в CSS | Плотность экрана | Какой PNG нужен |
| --- | --- | --- |
| 24×24 | 1× | 24×24 |
| 24×24 | 2× | 48×48 |
| 16×16 | 2× | 32×32 |
| 24×24 | 3× | 72×72 |

Нельзя растянуть PNG 16px через CSS и честно назвать это retina.

### Как отдавать retina PNG

```html
<img
  src="/icons/check-24.png"
  srcset="/icons/check-24.png 1x, /icons/check-48.png 2x, /icons/check-72.png 3x"
  width="24"
  height="24"
  alt=""
/>
```

`width`/`height` (или CSS) держат **место в вёрстке** — 24 CSS‑пикселя. `srcset` подкладывает достаточно пикселей экрана. Путаница этих двух вещей как раз и рождает тикеты «в SVG было чётко, в PNG — мыло».

### Перед экспортом SVG → PNG

1. `viewBox` совпадает с реальными границами рисунка — без неожиданной обрезки  
2. Сначала реши, **каким CSS‑размером** будешь показывать (письмо, CMS — неважно)  
3. Умножь на нужную плотность экрана — и только потом экспортируй  
4. Прозрачность лучше белого фона; белый — только если площадка иначе не принимает  
5. Если площадка умеет SVG (обычный современный интерфейс) — PNG часто не нужен  

Когда экспорт «мягкий», а path в порядке, не гадай: вставь разметку, подгони `width`/`height` по превью и скачай PNG. В [конвертере SVG → PNG](https://getsvgeditor.com/svg-to-png) экспорт идёт в **2×** от размера SVG — как раз под типичный retina‑слот: показал на 24 CSS px, в файле 48 px.

## Inline SVG, img и React‑компонент

| Способ | Как задаёшь размер | Цвет под тему | Когда уместен |
| --- | --- | --- | --- |
| `<img src="*.svg">` | CSS на самой картинке | Слабо (`currentColor` из файла не подхватится) | Логотипы, контент в CMS |
| Inline SVG | CSS + атрибуты | Хорошо | Разовая иллюстрация на странице |
| React / RN‑компонент | props и токены | Хорошо | Иконки дизайн‑системы, повторяющийся интерфейс |

Баги размера бывают во всех трёх случаях. Компонент просто делает договорённость явной: **`viewBox` в файле, размер — в месте вызова**.

Если нужно сравнить ещё и background со sprite — это уже отдельный разговор: та же тема, другое решение.

## Краевые случаи

Это как раз те баги, про которые говорят «viewBox у нас и так есть» — и они всё равно уезжают в прод.

### 1. Нет ни одного размера → баннер 300×150

Нет размера в CSS, нет корневых `width`/`height`, остался один `viewBox` — многие движки падают на запасной размер SVG, часто **300×150**. Иконка 24 превращается в баннер. Задай размер через CSS или `size`, либо оставь нормальные атрибуты, если файл не в компоненте.

### 2. SVGO снял лишнее — и чуть больше, чем надо

Оптимизаторы могут убрать `width`/`height` (для системы иконок это нормально) или переписать `viewBox`. Настрой SVGO так, чтобы **контракт** оставался. Убрать размер отображения — можно. Убрать или выдумать `viewBox` — нельзя.

### 3. Transform’ы и группы из Figma

Экспорт может завернуть рисунок в `<g transform="translate(...)">`, а корневой бокс при этом не совпадает с реальной графикой. Нормализуй один раз (объединение, разворот transform, политика «Outline stroke») — и не правь path вручную в каждом PR.

### 4. `vector-effect="non-scaling-stroke"`

Когда иконку тянут с 16 до 32, тонкие линии толстеют, если не включён non‑scaling stroke. Решите для всей системы: линии растут вместе с иконкой (обычное поведение) или толщина на экране должна оставаться примерно той же. В одном наборе два подхода лучше не мешать.

### 5. Жёсткий `#000` плюс неверный размер = «иконка сломана»

Неверный цвет и неверный размер часто приходят одним тикетом. Для иконок интерфейса бери `currentColor` или CSS‑переменные — тогда цвет и размер не путаются в одну кучу.

### 6. Почтовые клиенты

Многие почтовики плохо дружат с inline SVG. Заранее планируй PNG (обычно 2×), а в шаблоне держи слот 1×. `currentColor` в письмах почти никогда не сработает как в вебе.

### 7. `width="100%"` без явной высоты

Проценты считаются от родительского блока. SVG с `width="100%"` без высоты и без `aspect-ratio` может схлопнуться, растянуться через `preserveAspectRatio="none"` или поймать ловушку 300×150 — зависит от окружения. Для иконок лучше абсолютный размер по умолчанию или prop `size`, не проценты.

### 8. `overflow` и «пропавшие» линии

У корневого SVG во многих браузерах по умолчанию `overflow: hidden`. Если рисунок почти касается края `viewBox`, при масштабе может обрезаться сглаживание штриха. Либо оставь небольшой внутренний запас в сетке 24, либо осознанно поставь `overflow="visible"`. Не раздувай `stroke-width`, пока не убедился, что дело именно в обрезке.

## Проверка иконки за 60 секунд

Перед мержем или перед растром:

1. **`viewBox` честный?** Не ставь `0 0 24 24`, если рисунок на самом деле `0 0 20 20`.  
2. **Атрибуты `width`/`height` дублируют то, что уже задаёт CSS?** Убери или приведи к общему токену.  
3. **В JSX место вызова может переопределить size и `aria-*`?** Смотри порядок `{...props}`.  
4. **На интерфейсной иконке зашит `#000`?** Лучше `currentColor`.  
5. **Нужен PNG?** Размер в CSS → умножить на плотность экрана → экспорт. Маленький растр не растягивать.  
6. **`preserveAspectRatio` не воюет с неквадратной коробкой?** Проверь до обвинений в адрес path.  
7. **Нет ни CSS, ни атрибутов?** Имей в виду дефолт 300×150.  
8. **`getBBox()` и `viewBox` согласованы?** Если нет — сначала контракт, потом стили кнопки.  
9. **Тонкая линия обрезана на краю фрейма?** Смотри `overflow` и внутренние поля, не только `stroke-width`.

## Договоритесь о размере один раз на всю команду

Запишите правила — и не открывайте этот спор заново в каждом PR:

| Слой | Решение |
| --- | --- |
| **В макете** | Один квадратный `viewBox` — 24 *или* 20, но не оба сразу |
| **В вебе** | Компоненты с `size` и `currentColor`; path под каждый экран не правят |
| **В почте и на старых площадках** | PNG в 2×, в шаблоне размер = 1× CSS‑слот |
| **В пайплайне** | SVGR (или аналог), если `.svg` идут потоком; разовая вставка в JSX — когда нужен один компонент и живое превью прямо сейчас |

Три размера никуда не денутся. В проде спокойно только когда **спорить разрешено одному** — и это должен быть размер в месте вызова, а не сюрприз внутри файла.

### Когда следующая иконка снова «сломана»

Не начинай со `stroke-width`. Спроси, какой из трёх сигналов победил:

1. Честный ли `viewBox`?  
2. Не перебивают ли атрибуты CSS или props?  
3. Если нужен растр — ты экспортировал **размер в CSS × плотность экрана**, а не размер из атрибутов SVG?  

Вставь разметку, сверь контракт с превью, задай размер там, где иконку используют, и делай PNG только если площадка SVG не принимает.

Контракт — в файле. Спор о размере — в месте вызова. Крошечные «марки» и мыльные PNG после этого обычно пропадают сами.
